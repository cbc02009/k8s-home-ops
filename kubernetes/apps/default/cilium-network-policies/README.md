# CiliumNetworkPolicies for the `default` namespace

Generated by **kguardian** (`generate_network_policy`, `policy_type=cilium`) from
observed eBPF traffic of every running workload in the `default` namespace on
**2026-11-15**. One policy per workload, least-privilege: any traffic not
explicitly allowed is denied.

Deliberate edits on top of the kguardian output (mechanical, no rule changes):

- dropped `k8s:pod-template-hash` from all selectors — the raw output anchored
  policies to one ReplicaSet generation, which would silently un-protect pods
  after the next rollout;
- renamed `metadata.name` to `<workload>-cnp`.

The Kustomization in `ks.yaml` applies all policies when this section is
reconciled. They are applied **enforcing**: there is no audit mode here.

## Review checklist before merging

1. **No-egress policies deny ALL egress** (incl. DNS) once applied. In the
   table above, an egress-rules count of 0 means the pod produced no captured
   egress during the observation window — adding a DNS-egress rule (or
   removing the policy) is a judgment call per workload.
2. `qbittorrent` carries ~3.1k `/32` CIDR egress entries (observed swarm
   peers + ports). That is the faithful least-privilege set, but it will grow
   and shrink as the swarm does; expect to widen it (e.g. to the tracker
   CIDRs or untracked egress) if you want it to be a working policy rather
   than a snapshot.
3. Ingress rules reference peers by stable `app.kubernetes.io/*` labels
   (arr stack, envoy-gateway, coredns, ...). No `pod-template-hash`
   anywhere, so rollouts on either side keep matching.
4. `prune: true` — deleting a policy file from this dir deletes the in-cluster
   CNP on the next reconcile.

## Re-running

Re-generation is a one-shot: the kguardian llm-bridge at
`kguardian-llm-bridge.kguardian.svc.cluster.local:8080` answers
`tools/call` `generate_network_policy` with `pod_name` for each running pod.
